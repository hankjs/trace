CLI 那头的架子搭好了，这一篇我们把飞书这头接上。这一节的具体目标是：你在群里 @机器人 说一句话，你的程序能收到，并且回一句消息。

如果你在网上搜过任何「聊天机器人开发」教程，大概率见过这样的第一步：准备一台云服务器、买个域名、配 HTTPS 证书、写一个 webhook 接口、在平台后台填回调地址……还没写到业务代码，先交了一个月服务器钱。我之前接入企业微信客服的亲身经历就是这样，非常麻烦。

这一篇完全不用这么麻烦，因为飞书提供了一种对个人开发者极其友好的接入方式，我们先把它的原理讲明白。

谁连谁，这是个大问题

平台要把「有人给机器人发消息了」这件事告诉你的程序，无非就是两个方向。

webhook 模式：平台连你。 你暴露一个 HTTP 接口，平台有事就往这个地址推。问题在于你的程序必须能被公网访问到。家里的电脑没有公网 IP，平台根本找不到你。所以才需要云服务器、域名、证书那一套。

长连接模式：你连平台。 你的程序启动时主动向飞书开放平台发起一条 WebSocket 连接并保持不断，之后所有事件都从这条连接推下来。不需要你有任何公网身份，你家的网络能打开飞书网页，就能建立这条连接。

一句话总结就是：webhook 要求你是个线上的「服务器」，长连接只要求你是个「客户端」就可以。

/**
 * 飞书接入：WS 长连接收消息 + REST 回消息。
 */
import * as Lark from '@larksuiteoapi/node-sdk';

export interface IncomingMessage {
  messageId: string;
  chatId: string;
  chatType: string; // 'p2p' 单聊 | 'group' 群聊
  messageType: string; // 'text' | 'image' | 'post' | ...
  text: string; // text 消息的正文（其他类型为空串）
  senderOpenId: string;
}

export interface BotOptions {
  appId: string;
  appSecret: string;
  onMessage: (msg: IncomingMessage, bot: Bot) => Promise<void>;
}

export interface Bot {
  client: Lark.Client;
  reply: (messageId: string, text: string) => Promise<string | undefined>;
}

function extractText(messageType: string, content: string): string {
  const parsed = JSON.parse(content);
  if (messageType === 'text') {
    return parsed.text ?? '';
  }
  if (messageType === 'post') {
    const paragraphs: any[][] = parsed.content ?? [];
    return paragraphs
      .flat()
      .filter((el) => el.tag === 'text')
      .map((el) => el.text)
      .join('')
      .trim();
  }
  return '';
}

export function startBot(opts: BotOptions): Bot {
  const { appId, appSecret, onMessage } = opts;

  const client = new Lark.Client({ appId, appSecret });

  const bot: Bot = {
    client,
    async reply(messageId, text) {
      const res = await client.im.v1.message.reply({
        path: { message_id: messageId },
        data: { msg_type: 'text', content: JSON.stringify({ text }) },
      });
      return res.data?.message_id;
    },
  };

  const dispatcher = new Lark.EventDispatcher({}).register({
    'im.message.receive_v1': async (data) => {
      const m = data.message;
      const msg: IncomingMessage = {
        messageId: m.message_id,
        chatId: m.chat_id,
        chatType: m.chat_type,
        messageType: m.message_type,
        text: extractText(m.message_type, m.content),
        senderOpenId: data.sender.sender_id?.open_id ?? '',
      };
      await onMessage(msg, bot);
    },
  });

  const wsClient = new Lark.WSClient({ appId, appSecret });
  wsClient.start({ eventDispatcher: dispatcher });

  return bot;
}


这个文件里有三个角色，各自的职责很清楚：

Lark.Client 管出。所有主动调 API 的动作——发消息、回消息、以后的传图片、改卡片都走它。它拿着 App ID 和 Secret 自己维护鉴权 token，你不用操心过期刷新。

Lark.WSClient 管进。它负责建立并维持那条 WebSocket 长连接，断了自动重连。

EventDispatcher 管分发。长连接上下来的事件五花八门，dispatcher 按事件名路由到对应的处理函数。今天只注册了 im.message.receive_v1 一个，后面的入群事件、卡片点击事件都会挂到这里。

解析消息时有个所有人都会踩一次的坑：content 字段是「JSON 字符串」，套在事件 JSON 里面。也就是说 SDK 把外层事件解析好了，内层的 m.content 还是个字符串，得再 JSON.parse 一次才能拿到 { "text": "..." }。双层 JSON，飞书协议就是这么设计的，记住就好。

还有一个容易踩的坑：你在群里 @机器人 发消息，实际收到的 message_type 可能是 post（富文本），而不是你以为的 text。post 的 content 结构完全不同——文本被拆散在一个嵌套数组里，每段内容都标了 tag（text、at、img 等）。这就是 extractText 做的事：不管来的是 text 还是 post，都能把纯文本提出来。

另外注意 IncomingMessage 这个接口——我们没有把 SDK 的原始事件结构直接往外传，先收敛成自己定义的干净类型。

/**
 * Agent OS 入口。
 * 当前阶段：连上飞书，收到消息原样回一句（echo bot）。
 */
import 'dotenv/config';
import { startBot } from './im/lark.js';

const appId = process.env.BOT_A_APP_ID;
const appSecret = process.env.BOT_A_APP_SECRET;

if (!appId || !appSecret) {
  console.error('缺少 BOT_A_APP_ID / BOT_A_APP_SECRET，请检查 .env');
  process.exit(1);
}

console.log('Agent OS 启动，正在建立飞书长连接…');

startBot({
  appId,
  appSecret,
  onMessage: async (msg, bot) => {
    console.log(`[收到] chat=${msg.chatId} type=${msg.chatType} sender=${msg.senderOpenId} 内容: ${msg.text}`);
    const replyId = await bot.reply(msg.messageId, `收到：${msg.text}`);
    console.log(`[已回] message_id=${replyId}`);
  },
});


onMessage 里现在只有三行：打日志、原样回一句、再打日志。echo bot 是通信链路的听诊器——它什么业务都不做，就为了证明「收得到、回得去」。

群里同时出现了机器人的回复：「收到：@_user_1 你好，在吗？」

通了。手机上发一句，家里跑的进程秒回——没有服务器，没有域名，没有内网穿透工具。

回复内容里有个奇怪的 @_user_1，这里先解释一半：飞书把消息里的 @ 换成了占位符，被 @ 的人是谁放在事件的另一个字段里。下一篇会把占位符还原成人名，并把完整的提及信息整理出来。

还有一个现象值得你亲手验证：在群里发一句不带 @ 的话，终端安安静静，什么都没收到。

顺手拿到你自己的 open_id

日志里的 sender 字段值得单独说。飞书里每个人在每个应用视角下有一个 open_id（ou_ 开头），机器人想 @某个真人，靠的就是它。而这套系统后面有个关键场景全指着这件事：危险操作要 @你 拍板——机器人得知道「你」是谁。

拿到它最省事的办法就是你眼前这个 echo bot：你自己在群里给机器人发条消息，日志 sender= 后面那串 ou_ 开头的值就是你的 open_id。不用调任何额外接口，不用申请任何新权限。把它记进 .env，往后审批、通知的篇章直接用：

.env
复制
OWNER_OPEN_ID=ou_你日志里看到的那串


拿到之后立刻能玩：@真人 的消息语法是在文本里嵌一个 at 标签——

typescript
复制
await bot.reply(msg.messageId, `<at user_id="${process.env.OWNER_OPEN_ID}"></at> 收到，这条是点名回复`);


发出去后你会在群里看到自己被蓝色的 @ 点名，手机上会有提醒。这就是后面「审批」体验的雏形。

顺带一提，平台还有一个按群拉成员列表的接口（im/v1/chats/{chat_id}/members），能一次拿到群里所有人的 open_id，但它需要单独申请「获取群信息」类权限。现阶段日志这条路已经够用，等做审批门需要枚举群成员时再去开也可以。

最后

echo bot 证明了链路通畅，但它现在对消息的理解还很粗糙：@ 是个占位符没还原、话题群和普通群不分、发图片给它就直接漏掉。下一篇我们把消息解析做扎实——重点是话题群：为什么「一个话题 = 一个任务」是整个系统最顺手的组织方式，以及怎么把回复精准地钉进对应的话题里。
